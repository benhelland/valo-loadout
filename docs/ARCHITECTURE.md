# Architecture

The stack below is locked in (decided 2026-08-28, optimized for near-$0 cost at personal-project scale). Data model and subsystem design remain sketches to refine as building starts.

## High-level shape

```
[valorant-api.com]  --sync job-->  [our DB: skins cache]
                                          |
[browser] <--REST/RPC--> [app server] ---+---> [our DB: users, loadouts, wishlists]
                                          |
                                          +---> [store-check subsystem] <--Riot auth-->[Riot's servers]
                                                        |
                                                        v
                                                 [notification dispatch] --> [Discord webhook (v1); email/push later]
```

Three subsystems that should stay loosely coupled:

1. **Content layer** — skin/cosmetic catalog, synced from valorant-api.com. No user data, no auth. Could be static-generated or cached aggressively since it changes on Riot's release cadence, not per-request.
2. **App layer** — accounts, loadouts, wishlists. Standard CRUD web app. Doesn't need to know anything about Riot's internal APIs.
3. **Store-check subsystem** — the one part of this app that touches Riot's unofficial/internal endpoints. Keep this isolated (own module, own error boundaries) so the rest of the app degrades gracefully if this piece breaks or has to be disabled. See `RISKS.md` for why this isolation matters.

## Tech stack

Every piece below was picked to run on a free tier at this project's scale, with exactly one paid line item (vibe-tagging LLM calls, ingest-time only — a few dollars a year at most).

| Concern | Choice | Why |
|---|---|---|
| **Language** | TypeScript, everywhere (frontend, API routes, sync/job scripts) | One language across the whole app — no context-switching, shared types between frontend and backend. |
| **Frontend framework** | Next.js (React) | Strong fit for an image/video-heavy, animation-forward UI; good SSR/ISR story for the mostly-static skin gallery; one deploy target with the backend. |
| **Styling** | Tailwind CSS | Fast to build a polished, consistent UI without hand-rolling a design system. |
| **Backend** | Next.js API routes / route handlers | No separate service needed — the store-check subsystem is I/O-bound (a few HTTP calls per account per day), well within serverless function limits. |
| **Database** | Postgres via **Neon** | Serverless Postgres that scales to zero — no compute charge while idle, which fits bursty personal-project traffic. Free tier. |
| **ORM** | Prisma | Type-safe queries/migrations matching the TypeScript-everywhere choice; keeps the data model in `ARCHITECTURE.md` translatable directly into schema. |
| **Auth (our own accounts)** | Auth.js (NextAuth), **Discord OAuth only** | No password handling of our own to build or secure; fits the audience (already on Discord for notifications); sessions stored in the same Neon DB — no extra service. Free. |
| **Hosting** | Vercel (Hobby tier) | Free at this scale; pairs naturally with Next.js; one deploy target for frontend + API routes. |
| **Background job trigger** | Vercel Cron, falling back to a free GitHub Actions scheduled workflow hitting a protected API route if Vercel's free-tier cron granularity is too coarse for "check every 15-30 min for accounts whose `next_poll_at` has passed" (verify the actual Hobby-tier limit when building — don't assume) | Either way: $0. The route itself does the real work (query due accounts, poll Riot, upsert `skin_sighting_stats`, dispatch notifications) — the trigger is just what wakes it up. |
| **Images/video** | Direct URLs to valorant-api.com's CDN, rendered through Next.js's built-in image optimization/caching | We never re-host or mirror their assets ourselves — no S3/R2/object-storage bill, and it's the "good citizen" behavior `RISKS.md` already commits to. |
| **Color extraction** | A JS color-quantization library, run server-side during the sync job | Pure compute, no external API, no cost beyond the sync job's own runtime. |
| **Vibe tagging** | A vision-capable LLM API call, ingest-time only (new skins/chromas, not re-run on unchanged items) | The one real recurring cost in the stack — small, because it only runs at Riot's release cadence (a few hundred calls/year), not per request. |
| **Notification dispatch** | Plain outbound HTTP POST to a Discord webhook URL | No service, no SDK needed, free and effectively unlimited at this volume. Written behind a small `channel` abstraction (per `notifications_sent.channel`) so email/push can be added post-v1 without touching detection/dedup logic. |
| **Secrets/encryption** | Env vars (`.env.local`, never committed) + Node's built-in `crypto` (AES-256-GCM) for encrypting linked-account tokens at rest, keyed by `RIOT_TOKEN_ENCRYPTION_KEY` | No separate secrets-management service needed at this scale; matches the non-negotiables in `CLAUDE.md`. |

**Why one relational database and not a combination (Postgres + Mongo, or + Redis):** every table in this app has real structure and real relationships that need enforcing (a `loadout_item` must point at a `skin` that exists; gallery filtering means combining several facets — weapon, tier, color, vibe — in one query). That's exactly the workload relational databases are built for, and the data volume here (~15-20k catalog rows, user data scaling with actual usage) never approaches the point where NoSQL's tradeoffs (schema flexibility for wildly varying documents, horizontal write scaling) would pay for themselves. A second datastore would mean paying for and operating two services instead of one, for a data shape that doesn't need the split — directly working against the cost goal. Revisit only if a real bottleneck shows up (e.g. Postgres + Next.js ISR caching genuinely can't keep the gallery fast), not preemptively.

The one piece worth keeping regardless of any future stack changes: the store-check subsystem stays isolated from the app/content layers (see below).

**Auth (Discord OAuth, real - mock auth retired):** the loadout builder was originally built against a mock user (`getCurrentUserId()` upserting one hardcoded dev row), on explicit call - build the feature, wire up real accounts after. That swap has now happened: `src/lib/auth.ts`'s `getCurrentUserId()` reads a real Auth.js v5 session and either returns the signed-in user's id or redirects to `/sign-in` - it was genuinely the one-function change the mock-auth design promised, no call site in `src/actions/loadouts.ts` or any loadout page needed to change.

- **Split config, two files.** `src/auth.config.ts` holds only `pages`/`callbacks.authorized` - no `PrismaAdapter`, no Discord secret. `src/auth.ts` spreads that and adds the real adapter/provider/session config; only it is imported from Node contexts (the API route handler, server components/actions). `src/proxy.ts` (Next.js 16 renamed `middleware.ts` → `proxy.ts` mid-build, see below) imports the lightweight config only, so route protection is a pure JWT-cookie check with no DB round-trip on every navigation.
- **Session strategy is explicitly `"jwt"`, not left to default.** Passing an adapter makes Auth.js default to `"database"` sessions (confirmed by reading `@auth/core/lib/init.js` directly rather than assuming) - that would try to read/write a `Session` Prisma model that was deliberately never added to the schema (see its own comment: "JWT sessions - no Session table needed"). Getting this wrong would 500 every sign-in.
- **Two Prisma-adapter compatibility bugs found by reading `@auth/prisma-adapter` and `@auth/core`'s actual source before trusting the schema looked complete:**
  1. The OAuth login path (`handle-login.js`) unconditionally calls `createUser({ ...profile, emailVerified: null })`, even with no email provider configured. The `User` model had no `emailVerified` column - the very first Discord sign-in would have thrown a Prisma "unknown argument" error. Added `emailVerified DateTime?` (migration `20260830161116_add_user_email_verified`).
  2. Confirmed above: adapter presence flips the session-strategy default to `"database"` unless overridden.
- **Route protection is layered, not single-point.** `src/proxy.ts` gates `/loadouts/:path*` and `/account/:path*` and redirects to `/sign-in?callbackUrl=<path>` before a page or action ever runs (Server Actions are POSTs to the page's own route, so a matcher covering the page covers actions called from it too - confirmed against Next's own docs, not assumed). `getCurrentUserId()` independently re-checks the session and redirects again if it's ever reached without one - deliberate defense in depth, not redundant: it's what protects a server action if a future call site is ever added outside the matcher's paths, or the matcher drifts.
- **`callbackUrl` open-redirect handling.** Auth.js's own redirect builds `callbackUrl` as an *absolute* URL (`http://host/loadouts`), not a path. The buddy-picker's existing `safeReturnTo()` (`src/lib/safeReturnTo.ts`) only accepts relative paths by design, so passed an absolute URL it would silently reject and fall back to a default - losing exactly where the user was headed. Rather than widen `safeReturnTo`'s contract (shared with the buddy picker, which only ever produces relative paths), `/sign-in` strips any `callbackUrl` down to just its pathname+search *before* validating it (parsing against a throwaway base discards any origin - real or attacker-supplied - unconditionally), then runs that through the unmodified `safeReturnTo`.
- **`next-auth` v5 (`5.0.0-beta.32`) + `@auth/prisma-adapter`, Discord provider only** - no password of our own to build or secure, matches the original stack decision. Discord's avatar CDN (`cdn.discordapp.com`) added to `next.config.ts`'s image `remotePatterns` alongside `media.valorant-api.com`.
- **Next.js 16 renamed `middleware.ts` → `proxy.ts` mid-build** (same mechanism, clearer name - see `nextjs.org/docs/messages/middleware-to-proxy`); worth noting because the build error was misleading at first ("must export a function...") even though the exported value genuinely was one - Next's build-time check doesn't see through `export const { auth: proxy } = NextAuth(...)`'s destructuring, only a separately-named `export const proxy = ...` statement. Also notable: `proxy` defaults to the **Node.js runtime** as of v16 (previously Edge for `middleware`), which would have made the split-config Edge-compatibility concern moot anyway - kept the split regardless since a lightweight cookie-only check is still better than a DB round-trip per navigation on principle, not just for Edge compatibility.
- **What's *not* built (deliberately):** the Riot account-linking flow itself. See "Store-check subsystem" below and `docs/ROADMAP.md` Phase 3 - that piece is explicitly gated on switching models (Opus) before it's written, per `ROADMAP.md`'s own pre-existing instruction. `/account` (protected, built this pass) shows the required plain-language disclosure and a disabled "coming soon" control instead of a working - or worse, stubbed/fake - login form.
- **Known consequence, not fixed automatically:** the mock dev user's data (a real test loadout created against `dev@valo-loadout.local` during earlier build/QA passes) has no Discord `Account` row linked to it, so it's orphaned once real auth is live - there's no way for any real Discord sign-in to "become" that user. Left alone rather than guessing which real account it should migrate to.
- **Hand-off - the one thing left for the user to do:** create a Discord application at [discord.com/developers/applications](https://discord.com/developers/applications), add an OAuth2 redirect URI of `http://localhost:3000/api/auth/callback/discord` (and the equivalent `https://<production-domain>/api/auth/callback/discord` once deployed), and put its Client ID/Secret into `.env.local` as `AUTH_DISCORD_ID`/`AUTH_DISCORD_SECRET`. `AUTH_SECRET` is already generated and in place (a local JWT-signing key, safe to generate without external setup - regenerate anytime via `openssl rand -base64 32` if it should ever be rotated).

**Loadout builder implementation:** matches `PRD.md`'s "board layout" and "picker is the gallery's filter/search UI scoped to that weapon" directly - the picker (`/loadouts/[id]/weapon/[weaponId]`) reuses `FilterBar`/`SkinCard`/`Pagination` from the gallery itself (weapon filter hidden since it's locked by the slot), and assigning a skin (`/loadouts/[id]/weapon/[weaponId]/skins/[skinId]`) reuses the skin detail page verbatim (`SkinDetailView`/`SkinPreview`) with an added `loadoutContext` prop that surfaces an "Add to Loadout" action alongside the existing "Copy share link" one. Net-new code is mostly the board itself and the mutations, not a parallel picker/detail UI.

The board itself (`LoadoutBoard.tsx`) is a 4-column grid grouped by category (`BOARD_COLUMN_GROUPS` in `src/lib/weaponOrder.ts`: Sidearms | SMGs+Shotguns | Rifles+Melee | Snipers+Heavy), matching a reference loadout-chart layout supplied directly - every slot visible at once, buddy shown as an icon docked beside the weapon render in each tile. Clicking a filled tile pops up a small "View / Replace" choice instead of navigating immediately: View builds a `/combo/:encoded` link from that exact slot's skinId/levelId/chromaId/buddyId (so it shows the picked variant, not the skin's defaults - reusing the combo-link codec from "Sharing" below rather than a new mechanism), Replace opens the picker. Clicking an empty tile skips the popup and goes straight to the picker. (An earlier version instead mirrored the real client's own "category tabs + one weapon at a time" Collection-screen navigation - replaced once given this specific reference layout to build to instead.)

The assignment page (`.../skins/[skinId]/page.tsx`) also pre-fills the level/chroma/buddy selectors from the slot's existing item when it already holds this same skin, rather than resetting to defaults - re-opening a slot to tweak just the buddy shouldn't lose the level/chroma already chosen.

## Data model (sketch)

- `users` — id, email, auth info, created_at
- `linked_riot_accounts` — id, user_id, encrypted session token/cookie (never raw password), region/shard, last_synced_at, next_poll_at (derived from the account's own shop reset time, not a blind interval), status (active/expired/error/captcha_blocked), discord_webhook_url
- `skins` — id (`uuid` from valorant-api.com), weapon, name (`displayName`), tier/rarity (`contentTierUuid`), collection (`themeUuid` — confirmed the right field for this, not `bundles`), display_icon_url (`displayIcon`), price_vp_estimate (**not synced** — looked up from the static tier-price table at read time, see below), first_seen_in_sync_at (our own timestamp — see release-date note below), color_family (extracted from the base/first chroma's image) — synced, not user-editable. No `video_url`/`release_date` columns: video lives on levels/chromas individually (below), and valorant-api.com has no release-date field at all.
- `skin_levels` — id, skin_id, level_index, display_icon_url (nullable — confirmed some levels have none), video_url (nullable — confirmed most levels don't have one; `levelItem` from the API also gets stored, a raw enum like `EEquippableSkinLevelItem::SoundEffects` worth mapping to friendly text for the level-selector UI) — a skin's upgrade tiers, needed for the detail-page level selector
- `skin_chromas` — id, skin_id, chroma_index (the chroma's position in valorant-api's own array for that skin - index 0 is always the base/default color, recolors follow; without an explicit order a query returns chromas in unspecified order, and code assuming "chromas[0] is the default" can silently pick a recolor instead - confirmed bug, fixed by adding this column and ordering by it everywhere), display_icon_url, swatch_color (nullable — confirmed the base/default chroma usually has no swatch image; color extraction falls back to `fullRender`/`displayIcon` when swatch is missing), color_family (extracted, per-chroma — a color filter match can come from any chroma, not just the default), video_url (nullable — confirmed some skins' base chroma has no dedicated video at all, because the per-level videos already cover that color; the detail page falls through to the active level's video in that case rather than showing no animation) — color variants, needed for the detail-page swatch swap
- `skin_vibe_tags` — skin_id, tag (e.g. "dark", "sleek", "futuristic") — many-to-many, AI-assigned at sync time (see below); a skin can carry several tags
- `buddies` — id (from valorant-api.com), name, display_icon_url — synced, not user-editable
- `buddy_levels` — id, buddy_id, charm_level, display_icon_url — confirmed buddies have their own level progression too (charm growth stages), no video
- `loadouts` — id, user_id, name, created_at, is_shareable (bool, opt-in per loadout), share_slug (nullable, unguessable — regenerated on revoke)
- `loadout_items` — loadout_id, weapon_slot, skin_id, level_id, chroma_id, buddy_id
- `wishlist_items` — user_id, skin_id, added_at
- `skin_sighting_stats` — linked_riot_account_id, skin_id, first_seen_at, last_seen_at, times_seen — one row per (account, skin) ever seen in that account's shop, **upserted** on every poll for every skin observed that day (not just wishlist matches). Bounded by catalog size (at most ~1 row per skin that ever exists, per account), not by time — grows to a ceiling and stops, unlike a per-day log. Powers "last seen N days ago" / "seen N times since you signed up."
- `notifications_sent` — id, user_id, skin_id, channel, sent_at (dedupe so the same rotation doesn't notify twice — check for an existing row since the account's last reset before sending)

## Store-check subsystem detail

This is the part that carries actual risk (see `RISKS.md`) and deserves care:

- **The password flow described here originally is dead, and was never built.** It called for submitting username/password to Riot's auth endpoint and handling a 2FA code step. Checked against the live API before implementing (2026-08-31): `PUT https://auth.riotgames.com/api/v1/authorization` now requires an **hCaptcha token** as a mandatory field of `riot_identity`, and the community API docs themselves now warn that "authenticating directly is prone to breakage (captchas and cloudflare anti-bot)" and recommend cookie reauth instead. Obtaining that token programmatically means defeating bot detection — out of bounds for this project, and `RISKS.md` already conceded this flow "cannot solve" a CAPTCHA. What changed since scoping is severity: CAPTCHA went from an occasional per-account edge case to the default path for everyone. **Consequence: `PRD.md`'s "handles 2FA / code-entry step" requirement is moot** — we never reach a 2FA challenge because we never submit a password.
- **What's built instead — cookie reauth, no password, ever.** This is the option `CLAUDE.md` already named as preferable ("or better, use cookie/token-based re-auth so the password is never touched by our servers at all"), and it's what the reference implementation converged on too: SkinPeek's README states it "only uses [credentials] to get the cookies", and it shipped a `/cookies` command to skip passwords entirely.
  1. The user signs in to Riot themselves, in their own browser, clearing whatever challenge Riot shows them — legitimately, as themselves. They paste us the resulting `ssid` cookie.
  2. `assertUsableSsid` (`src/riot/ssid.ts`) validates it before it can reach a request or the database. It's interpolated into a `Cookie` header, so a value containing CR/LF would be header injection; the allowed set is RFC 6265's `cookie-octet`. Unit-tested (`src/riot/ssid.test.ts`).
  3. `createSessionFromSsid` (`src/riot/auth.ts`) exchanges it at `GET https://auth.riotgames.com/authorize?…` with `redirect: manual`. Tokens come back in the **URL fragment** of the `Location` header. A redirect to `authenticate.riotgames.com` instead means the session is dead → status `EXPIRED`, no retry.
  4. In parallel: `GET /userinfo` (puuid + game name/tag line), `POST entitlements.auth.riotgames.com/api/token/v1` (entitlements token), `PUT riot-geo.pas.si.riotgames.com/pas/v1/product/valorant` with the id_token (→ `affinities.live`, the shard the storefront is addressed by).
  5. `POST https://pd.{shard}.a.pvp.net/store/v3/storefront/{puuid}` with an empty JSON body. **Note v3/POST** — the community docs still document a `GET v2` that no longer works; the v3 shape came from reading SkinPeek's `shop.js`. Read fields are `SkinsPanelLayout.SingleItemOffers` and `…RemainingDurationInSeconds` and nothing else (bundles, night market, accessories and Radianite offers are all deliberately ignored).
  6. `SingleItemOffers` are **skin *level* UUIDs, not skin UUIDs** — mapped to skins via our existing `skin_levels` table. Unmapped ids are skipped, not fatal (a brand-new skin just means the catalog sync hasn't run since it shipped).
  7. Only the `ssid` is persisted, AES-256-GCM encrypted (`src/lib/crypto.ts`, unit-tested including tamper detection on ciphertext, auth tag, and IV). Access/entitlements tokens are never stored — they're minted fresh per poll and discarded.
- **Session longevity is the real UX cost:** an `ssid` alone is stable for roughly a week (all auth cookies ≈ three weeks), so users must periodically re-link. Riot sometimes rotates the cookie during reauth; `extractSsid` captures the new value and rolls it forward, which is the difference between staying linked and expiring on schedule.
- **CAPTCHA / hard-block handling:** kept, and now the primary failure mode rather than an edge case. `src/riot/http.ts` detects Cloudflare's `403` + `x-frame-options: SAMEORIGIN` signature (and treats `429` the same way), raising `RiotError("BLOCKED")` → status `CAPTCHA_BLOCKED`, surfaced plainly and **never retried**. Explicitly *not* implemented, and not to be added later without revisiting `RISKS.md`: proxy rotation, TLS-fingerprint spoofing, CAPTCHA solving. SkinPeek shipped a proxy manager for exactly this; that is bot-detection evasion and is the behaviour `RISKS.md` says draws attention.
- **Where the poller runs is an open question, so the trigger is pluggable.** Cloudflare is hardest on datacenter IPs — and every free scheduler in the planned stack (Vercel Cron, and the documented GitHub Actions fallback) is datacenter IPs. SkinPeek's own advice was "try hosting on your own PC". Two interchangeable triggers therefore exist, both thin wrappers over the same `runDueShopChecks()`: `GET /api/cron/check-shops` (Bearer `CRON_SECRET`, compared with a constant-time `safeEqual`, fails closed with 503 if the secret isn't configured) and `npm run check-shops` (runs anywhere, including a residential connection). Which one to actually use should be settled with evidence from a real deployment, not guessed. Running the job somewhere it isn't blocked is not evasion; rotating IPs to dodge a block would be.
- **Rate limiting** (`src/riot/http.ts`): every outbound Riot call goes through one `riotFetch()` so the guards can't be bypassed by a new call site. A 250ms minimum interval serialises bursts, and a per-process cap of 500 calls is a circuit breaker for the runaway-loop case. Honest limitation: both are per-process, so on serverless each cold start gets a fresh budget — the real cadence control is `nextPollAt` in the database (one poll per account per day, jittered up to 30 min so accounts don't sync up).
- **Never logging credentials** is enforced structurally, not by convention: the reauth `Location` header *contains the access token in its fragment*, so `redactUrl()` strips everything but origin+path, and `recordFailure` persists only messages this codebase authored — never an upstream error body.
- **Polling cadence:** one poll per account per day — the shop only resets once daily, so there's nothing to gain from checking more often. The storefront response includes when that account's shop next resets; store that as `next_poll_at` and poll shortly after it, jittered per account so many accounts don't all hit Riot at the same moment. If that scheduled poll fails (network error, Riot-side hiccup), a bounded retry with backoff later the same day is reasonable — but that's an exception path, not the routine cadence.
- **Data minimization:** only fetch and store what's needed to detect wishlist matches and update `skin_sighting_stats` (current shop skin IDs), not a full account/inventory dump, unless a feature actually needs it.
- **What "the shop" means here:** each account's storefront is (as of writing) 4 skin offers, replaced wholesale on that account's own ~24h reset cycle — once a rotation passes, those specific offers aren't purchasable again until they're randomly re-rolled some future day. This is public knowledge about the game, not something confirmed against a live API response — verify the actual storefront response shape (field names, offer count, reset-time field) against a real call when this phase is built, the same caution already applied to valorant-api.com. Note this is a different rotation from the Night Market or the accessory (buddy/spray) store, both out of v1 scope.

## Skin/animation assets

Schema confirmed against the live API on 2026-08-28 (`weapons`, `weapons/skins`, `weapons/skinchromas`, `weapons/skinlevels`, `buddies`, `contenttiers`, `themes`, `bundles`). Re-verify again before building if much time has passed — this is still an unofficial, unversioned API. It covers weapons, skins, chromas, levels, buddies, content tiers, themes, and bundles, with image assets per item; video (`streamedVideo`) lives on individual levels and chromas, not a single field per skin, and is frequently absent even where you'd expect it (only some levels/chromas have it). Cache/mirror what's needed (image and video URLs, keyed by id) rather than hitting valorant-api.com on every page load — it's a shared community resource, be a good citizen of it.

**Two gaps confirmed by directly probing the API — nothing hidden, just doesn't exist here:**

- **No VP price data anywhere** (not on skins, bundles, or weapons; probed for a dedicated prices/offers endpoint directly — none exists). **Resolution:** a small static `content_tier_id -> estimated_vp_price` lookup table (Select/Deluxe/Premium/Ultra/Exclusive have had fairly stable prices historically), not a per-skin DB column. Surfaced in the UI as an estimate, not a guarantee. **Stretch goal:** once Phase 3's authenticated Riot session exists, real prices are available from the same internal storefront endpoint already being called for shop tracking — could backfill/replace the estimates for skins that session happens to expose pricing for. Not blocking v1.
- **No release date anywhere** (not on skins, themes, or bundles). **Resolution:** `first_seen_in_sync_at`, our own timestamp recorded the first time the sync job encounters a given skin id. This is accurate going forward — valorant-api.com updates promptly when Riot ships new content, so newly-added skins get a real date. The one-time backfill of the existing ~1400 skins won't have meaningful historical ordering from this field alone (they'll mostly share the date of our first sync run); be upfront about that rather than presenting false precision — "newest first" sort is exact for anything released after this project starts syncing, approximate for the historical catalog.

**No 3D model data exists in this or any other legitimate source.** A true drag/rotate 3D inspect view was considered and explicitly declined for that reason — see `RISKS.md`. Presentation stays 2D/video: high-res images, animation clips where available, zoom/transition polish.

**Buddy pairing:** buddies show as a small circular badge on the preview frame — mirroring how Riot's own store/inventory UI pairs a buddy with a skin (a badge, never glued onto the gun render). This replaced an earlier approach (composite the buddy icon onto the weapon's flat render at a per-weapon anchor point) that was tried, tuned, and shipped, but still read as a sticker pasted on a photo — an inherent ceiling of gluing two flat, mismatched-perspective images together, not something further anchor-tuning could fix. That version (`src/lib/buddyAnchors.ts`, `src/components/gallery/BuddyPreview.tsx`) is preserved in git history (see the commit that introduced the badge) if a future pass wants to revisit an on-weapon composite — e.g. with rotation/tilt to simulate a hanging charm, a grounding drop-shadow, and a strap line — rather than reintroducing the flat-anchor version as-is.

**Buddy gallery (`/buddies`):** a browse/reference grid of every buddy - denser than the skin grid (more columns, smaller cards) since buddy icons are small and low-res to begin with, with fuzzy search and a color filter mirroring the skin gallery's. No per-buddy detail page (there's nothing more to show than the name/icon already on the card). Reachable via a small secondary tab pair (`GalleryTabs.tsx`) shown on both `/` and `/buddies`, deliberately not promoted into the site's main top nav - the skin gallery stays the front door for "Gallery".

It doubles as the buddy picker for a skin. A "Browse all buddies" link on the skin detail page enters *pick mode*: the gallery takes a `returnTo` path (plus the in-progress `levelId`/`chromaId`, which are client-only state that would otherwise be lost on the round trip), cards become real links, and choosing one returns to exactly where the user came from with `buddyId` applied. Works unchanged from the loadout builder's assign page, since the return path is just wherever they already were. `returnTo` is attacker-controllable, so it's validated as a same-origin relative path (`src/lib/safeReturnTo.ts`) rather than trusted - an unchecked value here is an open redirect. In plain browse mode cards render inert (no hover, no link), because a hover state on something unclickable reads as a broken affordance.

**Buddy color extraction excludes the shared keychain clasp:** buddy icons all hang from an identical rendered brass clasp, which isn't part of any charm's actual design. The generic skin/chroma extraction (`extractColorFamily`, at the time picked the highest-priority Vibrant swatch regardless of population - population-weighted since, see "Color and vibe tagging pipeline" below) let that clasp win 456 of 884 buddies (52%) as "orange" - a single-pixel clasp swatch outranking the charm's own, much larger swatch purely by priority order. Two things had to be established before fixing it for real, not just documenting it:
  - **Not a fixed screen position.** Diffing pixels across ~60 buddy icons (`src/scripts/analyzeClasp.ts`) found only 0.1% of pixels position-stable across icons - charm size/hang varies enough that a crop can't isolate it. Ruled out cropping.
  - **Is a recurring color signature.** Sampling raw Vibrant palettes across 150 buddies (`src/scripts/analyzeClaspColor.ts`) found swatches with hue 15-55° (brass/gold/bronze) and lightness 10-75% show up as a top-6 swatch on up to 49% of *all* buddies regardless of the charm's real color, but always at a tiny population share - a handful of pixels out of ~20-30 total, because the clasp is thin and mostly hidden.

  `extractBuddyColorFamily` (separate from the skin/chroma path, since skins don't have this problem) uses that population gap: pick the best non-hardware-band swatch: if it holds a meaningful share of the image (≥12%), classify from the non-hardware swatches only; otherwise trust the hardware-band swatches (the charm plausibly really is gold/brass-colored). A flat "does the hardware band dominate the whole palette" version was also tried and scored worse - the clasp's color routinely splits across 3-4 of Vibrant's six swatch slots, so it can out-total a charm's single real swatch by sheer count even while visually tiny. Validated catalog-wide (`src/scripts/validateBuddyColor.ts`, deleted after use) against name-implied colors (Sapphire→blue, Ruby→red, Emerald→green, etc.): "orange" dropped from 456/884 (52%) to 189/884 (21%), and 18/33 name-color spot checks now match vs. a minority before. Remaining noise is concentrated in the episodic "Gold"/"Silver" reward buddies, which are solid metallic orbs where a large dark background-vignette swatch (a separate, much less universal artifact than the clasp) sometimes wins over the correct gold-band swatches - a known secondary gap, not the clasp problem, left alone since it affects a small, specific buddy family rather than the whole catalog. Buddy `colorFamily` was backfilled catalog-wide once the fix landed (bypassing the sync job's normal "only fill in nulls" rule, since this was correcting already-set values).

**Loadout sharing:** two independent mechanisms, both reachable from a Share popover on the loadout board and on each card in the loadout list.
- *Share link* (`/l/:shareSlug`) - opt-in per loadout, private by default. The slug is 16 random bytes (base64url), deliberately distinct from the loadout's internal id so a link can be revoked without deleting the loadout; revoking clears the slug outright, which is what actually kills links already in the wild. The public page takes no user id and renders its own read-only markup rather than reusing `LoadoutBoard`, which exists entirely to drive mutations a viewer must never be offered.
- *Share as image* - renders `LoadoutShareImage.tsx` (a fixed-1200px, presentation-only template, not a screenshot of the live board with its buttons and nav chrome) off-screen on demand, rasterises it with `html-to-image` at 2x, copies the PNG to the clipboard by default, and offers a download. Clipboard *image* writes are the fragile part (Firefox doesn't support them, and any browser blocks them outside a secure context), so that step is wrapped separately: a failure there still leaves a working downloadable image and says so, rather than failing the whole action.

On the Image tab, the badge is a moveable/resizable "fidget" (`DraggableBuddyBadge.tsx`) — drag anywhere within the frame, drag its small grip to resize between a fixed min/max (48–180px), position always clamped so the whole badge stays inside the frame regardless of size. On the Animation tab it snaps to a fixed default (top-right, 96px) and stops being interactive — dragging over playing video is a distraction, not something worth supporting. Position/size are plain component state, intentionally not persisted anywhere (not localStorage, not the URL): leaving the page and coming back always starts from the default, matching what was asked for. Switching levels/chromas doesn't reset a custom placement, since none of that remounts the component; only navigating away and back does.

The circular backing and resize grip ("chrome") auto-fade to fully transparent ~1.5s after appearing, leaving just the buddy icon visible - on first mount, and again every time the Animation tab is left (Image↔Animation always re-reveals it, even though a custom position/size survives that same switch unchanged). Grabbing the badge (to move or resize) instantly reveals the chrome again and holds it visible for as long as the drag continues, however long that is, then restarts the same ~1.5s countdown once released - a ref-gated timer, not a naive restart, so a fade that was already ticking before a grab can't fire mid-drag and hide the chrome out from under an active interaction.

**Gallery performance:** the catalog is large enough (1500+ skins across years, plus levels/chromas as separate rows) that the gallery grid needs virtualization and lazy-loaded images from day one, not as a later optimization. Video should not autoplay across an entire grid of results — load/play on hover or on opening the detail view only, both for user bandwidth and so we're not hammering valorant-api.com's CDN.

**Filter bar:** every control applies its filter immediately on change (`FilterBar.tsx`, a client component using `router.replace` on the current path+params — no Apply button). State still lives entirely in the URL, so results stay server-rendered/shareable/bookmarkable; only the controls themselves needed to become client-interactive, not the results grid. Any filter change resets `page` back to 1. The search field pairs that same debounced auto-apply with a separate predictive dropdown (`SearchAutocomplete.tsx` + the `searchSkinsAutocomplete` server action in `src/actions/search.ts`) — a small, fast, unpaginated lookup for jumping straight to one skin, distinct from the (slower, full-catalog) filtered grid the same typed text also drives. Both are fuzzy-matched through the same shared subsequence scorer (`src/lib/fuzzyMatch.ts` - not just substring, so e.g. "vct" or "eldervndl" surfaces "Elderflame Vandal" in both places consistently). The grid's fuzzy path (`listSkins` in `src/queries/gallery.ts`) can't rank in SQL, so when search text is present it fetches every skin matching the *other* filters, fuzzy-scores/sorts in JS, and paginates the ranked array instead of paginating in the database - a real behavior split from the no-search path (which stays a single indexed/paginated SQL query), acceptable at this catalog size (~1365 real skins, usually far fewer once other filters narrow it down). Reused as-is by the loadout picker, scoped to the locked weapon via an optional `weaponId` param on both.

**Color filter shows the chroma that actually matched, not always the default.** A color match can come from any of a skin's chromas (see `skin_chromas.color_family` above), so filtering by e.g. "green" used to still show every card's base/default render even when green only exists on some other recolor - confusing, since the card visibly didn't look green. `listSkins` now fetches each skin's full (small, bounded) chroma list instead of just the base one; `SkinCard` takes a `matchColor` prop and, only when the base chroma isn't the one that matched, swaps in that specific chroma's image and links with `?chromaId=...` instead of the plain skin link. The skin detail page already supported `?chromaId=` pre-selection (built for the combo-share/buddy-picker round trips), so clicking through lands directly on the matching recolor with no extra plumbing needed there. Deliberately color-only: vibe tags are per-skin, not per-chroma (tagged once from the base image at sync time - see below), so there's no per-chroma vibe data to match against, and adding it would multiply the vibe-tagging API cost by however many chromas each skin has for a much fuzzier signal than color.

The search box's text is owned as local state in `FilterBar`, not resynced from the URL after mount. An earlier version tried to resync a `defaultValue` prop that round-tripped back down through the same debounced `router.replace` used to apply the filter, which raced: a slower-resolving older keystroke's response could land after a newer one and stomp text the user had already typed further ahead of (visible as text getting randomly deleted then reappearing while typing). Being fully owned locally removes the race instead of trying to out-clever it. The "Clear" control is a plain `<a>`, not a soft `next/link` navigation, specifically so every control (the local search text, and the uncontrolled `defaultValue`-based selects) resets to its true default via a full page load, with no ambiguity about what survives a client-side transition.

**Default sort is rarity (highest first), not newest:** `firstSeenInSyncAt` is only meaningful for skins added after this project started syncing (see the release-date gap noted above) — nearly the entire backfilled catalog shares one timestamp, so "newest" wasn't actually a meaningful default order. Rarity-first also doubles as a better first impression for a gallery whose whole point is showing skins off.

**Color and vibe tagging pipeline (runs as part of the sync job, per new skin/chroma only — not re-run on unchanged items):**

- **Color:** extract a dominant-color bucket (red/blue/black/white/gold/multicolor/etc.) from each skin's and each chroma's display image via `node-vibrant`. Deterministic, no external API, cheap to (re)run.
  - **Two real bugs found and fixed after "black"/"white" returned zero results for every skin in the gallery filter** (user-reported, not caught during earlier buddy-color work even though it's the same file). First: `extractFamilyFromPalette` picked `swatches[0]` - whichever Vibrant-named swatch (Vibrant, then DarkVibrant, ...) happened to be non-null first, ignoring `population` (how much of the image it actually represents) entirely. Confirmed on real data: Reaver Vandal's "Vibrant" swatch had population 0 (a placeholder Vibrant.js synthesizes when it can't find real vibrant content) while its true dominant color sat in DarkMuted at population 24; Blackthorn Vandal's Muted swatch at population 76 lost to its own Vibrant swatch at population 10 purely on priority order. This was the same class of bug already found and fixed for buddy colors (see below) - it just hadn't been generalized to skins/chromas. Now population-weighted, filtering out zero-population placeholder swatches first. Second, and the actual reason black/white were *exactly* zero rather than just under-represented: `classifyHsl`'s thresholds (`lightPct<15` for black, `lightPct>92` for white) were dead zones no real render ever reaches. Histogrammed the population-weighted winning swatch's lightness across all 1318 real skins, among desaturated (satPct<12) results only: the darkest bottoms out at l=21%, the lightest tops out at l=81% - nothing anywhere close to the old cutoffs. That histogram showed three genuine clusters with natural valleys at ~35% and ~65% (dark ~20-30%, true-gray ~45-55%, light ~70-80%), which is what the thresholds are now set from - not another guess. Recalibrating `classifyHsl` affects buddy classification too, since it's shared: re-validated there as well (black 1→77, white 0→71, mostly reclaimed from an over-broad "gray" bucket, "orange" unchanged at 189 confirming the clasp-exclusion fix stayed intact) before backfilling. All three (skins, chromas, buddies) re-extracted catalog-wide with the fixed logic - free, since color extraction is local computation, no paid API involved, unlike vibe-tagging.
- **Vibe:** send each skin's showcase image to Claude Haiku 4.5 (`src/lib/vibeTagging.ts`) once at sync time, asking it to assign 1-4 vibe tags from a fixed 14-word vocabulary (not freeform, so filters stay consistent): dark, sleek, futuristic, elegant, aggressive, cute, retro, neon, anime, nature, gold, minimal, tactical, cosmic. Store the result in `skin_vibe_tags`; never re-tag on every request. This is an ingest-time cost (one call per new skin, maybe a few hundred/year at Riot's release cadence), not a runtime one. The image sent is `skin.displayIconUrl` - confirmed byte-identical to the base chroma's own `fullRenderUrl`/`displayIconUrl` for every skin checked (same dimensions, same file size), so it's already the best (and only) static render valorant-api.com offers for a skin, not a cut-down thumbnail. One real exception found by the full backfill: **the "Hi-DR0" collection (5 skins) serves 8192px-wide renders** - 16x the ~512px every other skin uses, and over Anthropic's 8000px per-dimension request limit. `tagSkinVibe` catches that specific 400 and retries once with the image downloaded, downscaled to 1568px (Anthropic's own documented sweet spot for image tokenization - not just "small enough to pass"), and sent as base64 instead of a URL. Self-healing for any future oversized image, not a one-off patch for just these 5.
  - **Prompt is a bulleted per-tag glossary, not a bare word list.** Each of ~1365 calls is an independent request with no memory of any other, so nothing keeps one call's idea of "sleek" consistent with another's unless the prompt pins every tag down itself (~$0.0002/skin extra for the definitions - negligible next to the consistency it buys). A first version wrote the definitions as one dense comma-joined sentence; live sample runs (`src/scripts/sampleVibeTagging.ts`, kept around for future re-validation) against a deliberately diverse skin set caught `tactical` over-triggering on anything that merely *looked* like a real gun silhouette - Minima Ares (flat, uniform matte black, zero pattern, zero attachments) kept getting tagged `tactical` even after the glossary text for that one tag explicitly excluded plain single-color guns. The exclusion clause didn't stick as prose *inside* a comma-run sentence; restructuring the whole prompt into a bulleted list (one line per tag) is what actually separated `tactical` from `minimal` cleanly - not a wording change. Several other suspected misses (Ayakashi not getting "anime", Araxys not getting "cosmic") turned out on directly viewing the images to be the model correctly reading what was actually in that specific render, not a defect - a good reminder to check the real image before trusting a hunch about what a skin "should" look like.
  - **Backfill (`src/scripts/backfillVibeTags.ts`):** a standalone catch-up script, separate from the per-skin sync path, for tagging an already-synced catalog with no vibe tags yet. Only ever queries skins with zero tags (`vibeTags: { none: {} } }`), so it's safe to interrupt and re-run - a partial run never re-spends on a skin already tagged and never duplicates tags. Each skin's tag-and-write is wrapped in its own try/catch so one bad image can't reject the whole in-flight batch, plus one automatic retry pass for anything that failed. Run against the full catalog (1318 real skins with images): 1313/1318 tagged on the first pass, the 5 Hi-DR0 failures identified and fixed as above, a second run of the same script (now self-healing) picked up exactly those 5 with no wasted spend on the other 1313 - **1318/1318 tagged, ~$1.15 total.**
- Both are best-effort classification, not ground truth — fine for a browse/filter feature, not something any other feature should depend on for correctness.

## Sharing

Both link types are read-only, need no viewer login, and stay entirely inside the app/content layers — no interaction with Riot's endpoints, no new risk profile.

- **Loadout links** (`/l/:share_slug`): the loadout is a real persisted row, so the link is opt-in (`is_shareable` flag) and points at `share_slug`, an unguessable id separate from the internal primary key — don't expose the internal id, so revoking/regenerating the slug is enough to kill an old link without touching the loadout itself. The page renders the loadout's live current state; no snapshot/versioning system needed for v1 — simplest option, revisit only if "the link changed on me" becomes an actual complaint.
- **Combo links** (`/combo/:encoded`): fully stateless — `:encoded` is the skin/level/chroma/buddy IDs packed into the URL itself (e.g. base62 or a short delimited string), not a database row. The route just parses the URL and renders the same skin-detail-with-buddy-overlay component the gallery already has. No auth, no save step, nothing to revoke.
- Neither route needs rate-limiting beyond normal web-app hygiene — they only ever touch our own DB/content cache, never Riot's endpoints.

## Security notes

- Encrypt linked-account tokens at rest; scope access to the store-check subsystem only.
- Never log raw credentials or tokens, including in error reporting.
- Rate-limit and monitor outbound calls to Riot's endpoints from our own infra so a bug can't turn into an accidental hammering incident.
